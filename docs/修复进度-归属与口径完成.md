## 一、本轮修掉的缺陷（按层分类）

### 1. 识别层（3 个，会让数字直接错）

| # | 缺陷 | 影响 | 修法 |
|---|---|---|---|
| 1 | `_invoice_amount_matcher` 兜底分支引用了未定义变量 `num` | `UnboundLocalError` 被吞，**上游两张发票的金额与票号从来没进过库** | 补 `num = float(v.replace(",",""))`，异常分支 continue |
| 2 | `classifier` 的 Excel 台账覆盖把「合同金额」写进结算单 amount | 下游结算被写成 7,990,500（合同额），真实结算额 7,922,962.05 被盖掉 | 只对合同类单据允许覆盖 amount/quantity；结算单等仅在 OCR 无值时才用台账值 |
| 3 | 回单的款项性质（保证金、退款）被并入货款合计 | 下游回款被算成 7,394,295，与台账差 59 万，**CRITICAL 误报** | 新增 `nature`（payment/deposit/refund），货款合计只累加 `payment` |

### 2. 归属层（单据找不到业务线）

- `_load_documents` 取字段时取的是**最早插入**那行；人工补录值更早，会把自动抽取的新值盖掉 → 改为按 `created_at / id` 取最新。
- `_bind_documents` 原来 `if not doc.contract_no: continue`，**没有合同号的单据根本进不了任何业务线** → 补三路归属：
  1. 合同号命中（原逻辑）
  2. 对手方公司名（去括号内容与「股份有限公司/有限责任公司/有限公司/国际贸易」后缀，容忍全半角）
  3. 金额锚点（采购合同额/采购结算额/付款额 → 上游；销售合同额/销售结算额/回款额/实收利息 → 下游）
  - 只有唯一命中一条业务线时才认，避免同客户的多条业务线互相抢单据。
- 修复 `_bind_documents` **把未归属单据直接丢弃**的问题：货权单这类既无合同号、又无金额和对手方主体的单据被无声丢掉，导致「库里有 4 份货权单」这条信息完全看不到 → 改为收集进 pool 一并交给检查逻辑。

### 3. 口径层（数字对了，但算法把重复/非货款算进去）

- 重复单据：同一张结算单存了两个副本（id 5 / id 17），下游结算被算成 15,845,924.1 → 同角色内「同合同号 + 同金额 + 同日期」判定为同一张单据，**金额只计一份、张数照实显示**，并出 INFO 说明。
- 非货款款项：保证金 596,250、退款 67,582.95 不参与货款勾稽，各自出 INFO。
- 下游回款比对口径：台账回款 6,757,500 是**本金**，实收利息 40,545 单列 → 期望值改为「本金 + 实收利息」= 6,798,045，与三张回款回单之和完全一致。
- 合同号脏值 `HSYC-TZS-2026-05-12)`（合同正文自写编号，带右括号）：不再当严重问题报。若单据金额能与台账锚点对上，降为 INFO 并说明「该编号为合同正文自写编号，与台账登记编号体系不同」。

## 三、货权单判向（按业务口径落地）

### 口径

> 「放货给云创 / 陕建的就是上游货权，其余均为下游。」

即：货权往我方（华山云创供应链科技）转 = 供应商把货权放给我们，属上游；货权再往终端客户转 = 下游。
与之配套的对手方口径：**上游为天柱深，下游为宏达**。

### 做法

货权单 / 放货通知既没有合同号、也没有金额，原来的归属规则（合同号 → 公司名 → 金额锚点）对它全部失效，
只能整批落进「方向未知」池 → 上下游各报一条「缺货权单」WARNING。改成两个判据：

1. **归属认业务线**：台账船名（本业务线为「法瑞」）必须出现在单据正文里。
   货权单必然写船名，这是它唯一能和台账对上的键；船名对不上就不归属，不猜。
2. **方向认接收方**：读正文「货权转移给谁 / 公司名称：…」的接收方公司名
   - 接收方含「云创」或「陕建」 → **上游**（我方主体接货）
   - 接收方是台账下游客户 → **下游**
   - 接收方是台账供应商 → **上游**
   - 接收方抽不到（如正文被 OCR 截断）但正文里出现我方主体（抄送行 CC）→ **上游**

实现：`DocRecord` 新增 `text`（正文前 3000 字），新增 `_cargo_receiver` / `_is_our_entity` / `_cargo_direction` / `_cargo_assign`；
`assign_documents` 第 0 步对货权单先跑这条，`_bind_documents` 对货权单改用 `_cargo_assign` 生成候选。

### 状态口径同步调整

7 条差异全为 INFO 后，若仍按「有任何差异 = 有警告」，页面上这条唯一跑通的业务线会显示「有警告」，
与事实（金额全部勾稽成功）相反。

- `service.run`：`elif SEVERITY_WARNING in severities → warning`，只剩 INFO 时落 `ok`；

- 列表排序改为 `error → warning → ok → no_data`：**已对齐的排在最前，未上传资料的沉底**
  （no_data 不是"待处理差异"，是"还没开始"，不该占首屏）。

## 五、无资料业务线单独分档（no_data）

### 问题

第一次跑全量对账，页面是「74 条业务线 / 已对齐 0 / 有警告 1 / 有错误 73」。
后 73 条经查是**一份资料都没上传过的业务线**：2×5 矩阵全 0，规则照样按「每格应有 1 份以上」推出 10 条 CRITICAL 缺件。
这 10 条不是差异，是「还没有资料」的同义反复，却把唯一那条真差异（YWX202605130004 的 9 条）压在 73 条红字底下。

### 做法

不是豁免缺件，而是**先分档再判差异**：

- 后端新增 `RECON_STATUS_NO_DATA = "no_data"`（`backend/models/reconciliation_report.py`），放进 `ALL_RECON_STATUSES`。
- `ReconciliationService.run` 里判 `has_docs = any(m.count > 0 for m in matrix)`：
  - 全 0 → `status = no_data`，计入 `no_data`，**并且不出差异**（`diffs = []`、`diff_count = 0`），说明放进 `payload.note`；
  - 有任何一份 → 原来的严格口径不变（CRITICAL 仍判 error），**缺件照旧算严重**。
- `_recompute_status` 增加 `has_docs`：忽略某条差异后重算状态时，no_data 的业务线不会被翻成 error/ok。
- 顺手修掉一个连带 bug：`_bind_documents` 返回的 pool（未归属单据）原先广播给了**每条**业务线，导致没有资料的业务线也被算成「有 5 份单据」、`has_docs` 恒为真、候选项恒有 10 个。改为只给「本身已绑定单据」的业务线做候选提示。
- 前端（`ReconciliationView.vue`）：汇总卡从 4 张扩成 5 张（总数 md=8、其余 4 张 md=4）；状态筛选、状态标签加「未上传资料」；列表「差异」列在 no_data 时显示 `—`；详情抽屉顶部显示 `note`，差异明细为空时给空态「尚未上传资料，暂无差异」。

## 六、P1 / P2 清单逐项收口

验证报告第六节的 P0–P2 清单，除「P1-3 缺件严重度」因上游付款回单缺失被你暂时搁置外，其余全部落地。
（以下实现的实测数据见第二节与第七节末尾的页面复核。）

### P1-1 感知哈希判重（原「同角色同合同号+同金额+同日期」不够用）

业务键去重只能拦住「字段完全读出且一致」的副本，扫描件一旦重拍/缩放、或字段抽空就失效。
新增 `backend/services/doc_dedup.py`（不引入新依赖、不做 DB 迁移）：

- `fingerprint(path)` → `(dhash16, width, height)`；PDF 取首页 100dpi 渲染，图片直接读；按「路径 + mtime」做 `lru_cache`，18 份资料首跑约 1s。
- 判同：**汉明距离 ≤ 1 且像素尺寸完全相同**。
- 为什么卡这么死：初版用「≤4 位 + 宽高比接近」，实测把 id1~id7（两张不同金额发票，dist=2）、id14~id15（两张货权单，dist=3）都误判成同图；收紧到 1 位并强制尺寸相等后，只有 id5~id17（dist=0、同为 1280×1852）命中，其余全部排除。
- 第二道保险：两边金额都读出且不同 → 不判重复。
- 差异文案区分来源：`image` 说明「dHash 一致且像素尺寸相同」，`business_key` 说明「合同号+金额+日期一致」。

### P1-4 结算单抽「最终结算金额」

验证报告说结算单金额靠 Excel 台账兜底——这条已经过时：三份结算单早就走 RULE 抽取。
真正的问题是规则靠通用金额 pattern 碰运气，而结算单正文同时出现「最终结算金额」「已收货款 7,990,545.00」「应补货款 -67,582.95」多个金额。

- `field_extractor.py` 新增 `_SETTLE_AMOUNT_ANCHOR`（标签 `最终结算金额|结算总金额|最终结算价款|结算金额|结算总额|结算价款`，容忍 `[:：]`、换行、任意个货币符号）。
- 新增 `_settlement_amount_matcher`（conf 0.97、rule `settlement_amount_anchor`、prio 99），插到 `_FIELD_RULES["amount"]` 首位，优先于通用金额规则。
- 踩坑：首版只容忍 2 个 `¥`，id 13 仍落到 `amount_total`；dump 清洗后文本发现货币符号被叠成 **`¥¥¥`（三个）**，改成 `[¥￥]*` 后三份全部命中。
- 实测：id5 / id17 = 7,922,962.05、id13 = 7,882,417.05，与台账完全一致（值未变，只是来源从"碰运气"变成"锚点确定"）。

### P2 业财对账单（一份文档合并多条业务线）

问题根因是分类，不是对账：id 11 的 `document_type = 对账单`，被 `_ROLE_KEYWORDS` 里 `ROLE_SETTLEMENT` 的「对账」关键词判成结算单，方向又判不出 → 进 `unlinked` 并报 `UNCLASSIFIED_DOC`。

三步修法：

1. `infer_role` 加前置规则：「对账」在文本且「结算单」不在 → 返回 `other`（真实结算单文件名都含「结算单」，不会误伤）。
2. `_statement_mentions(text, variants)`：先去空白再逐编号比对；完整编号找不到时退一步用 `-{year}-[0-9/]{0,40}{tail}` 匹配，容忍换行拆开与「HSYCXS (DD)\n-2026-0200/0236/0251」这种同行斜杠简写。
3. `check_business` 新增 `statement_docs` 参数：命中本业务线的对账单出一条 INFO「业财对账单已按合同号归属（多业务线合并单据）」，并写明金额不重复计入矩阵。
