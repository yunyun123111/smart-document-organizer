### 3.2 规则层实测：哪些对了、哪些不对

**✓ 正确的（这是本次验证最有价值的正面结论）**

1. **上游发票 ⇄ 采购结算**：两张上游发票 6,356,820.00 + 1,525,597.05 = 7,882,417.05，与采购结算金额分毫不差，系统未报差异——**多张发票可累加勾稽，规则成立**。
2. **下游发票 ⇄ 销售结算**：7,922,962.05 = 7,922,962.05，无差异。
3. **跨端利息**：下游结算 − 上游结算 = 7,922,962.05 − 7,882,417.05 = **40,545**，与台账 R 列应收利息、S 列实收利息同时命中，**未报 INTEREST_MISMATCH**。这条是全链路最核心的业务勾稽，规则设计（R/S 任一命中即通过）是对的。
4. **缺件不豁免**：文档齐了就不再报缺件，10 格全满后 8 条 MISSING_DOC 全部消失——说明此前的缺件报告确实是"归位失败导致的误报"，不是规则误判。
5. **尾款差额**：上游付款 7,950,000 − 采购结算 7,882,417.05 = 67,582.95，系统判 INFO「预付/尾款」，与真实的「天柱深退款 67,582.95」完全对上。

**✗ 不对的（3 条，都是口径/严重度问题，不是算法问题）**

**R-1（CRITICAL 误报）下游收款回单合计 7,394,295 vs 台账回款 6,757,500，差 +636,795**

回单实际构成：

| doc_id | 金额 | 真实性质 |
|---|---|---|
| 2 | 1,500,000.00 | 货款本金 |
| 4 | 3,400,374.00 | 货款本金（含利息 21,624） |
| 8 | 1,897,671.00 | 货款本金（含利息 18,921） |
| 12 | 596,250.00 | **保证金**（不是货款） |

6,757,500（本金回款）+ 40,545（利息，已含在 id 4/8 中）+ 596,250（保证金）= 7,394,295。
台账「回款」列只记本金，于是系统把保证金回单也算进"回款"里，报出 CRITICAL「回单合计超过台账回款额」——**性质上这是误报，会让真实有问题的业务线被淹没在此类噪声里**。

**R-2（severity 偏低）上游付款回单 1 份 67,582.95 vs 台账支付 7,950,000**

系统报 WARNING「回单未覆盖全部付款，可能分次付款」。方向判对了，但实际情况不是"分次付款"，而是**云创付天柱深的两笔 3,975,000（合计 7,950,000）付款回单在资料里根本不存在**——这是真实缺件，且缺的是对账最关键的付款凭证，应判 CRITICAL 而不是"可能分次付款"的 WARNING。同时 id=16 是**退款**回单（天柱深→云创），性质是收款，被计入"付款回单"格也不对。

**R-3（口径缺口，INFO 级但会长期存在）下游回款 6,757,500 vs 销售结算 7,922,962.05，差 −1,165,462.05**

真实勾稽是：回款 6,757,500 + 保证金 596,250×2 + 利息 40,545 = **7,990,545**（台账「收款」列），7,990,545 − 7,922,962.05 = 67,582.95（待退）。系统只拿「回款」比「结算」，永远差 1,165,462.05，无法区分"未回全"和"已收齐但含保证金与利息"。

**另有一条展示层缺陷**：down/settlement 格 `count=2 / amount=15,845,924.1`，因 id=5 与 id=17 是同一张结算单的两份副本（`file_size` 都是 127,593，`file_hash` 不同，系统按哈希判重所以没拦住）。矩阵金额翻倍虽未影响勾稽结论（勾稽用的是台账数），但页面会误导使用者。

## 八、结论

1. **可以做，但现在的识别层还撑不起对账。** 分类已达标（18/18），字段抽取达标率约 28%（金额 5/18、合同号 0/18），对账因此被"归位失败"打穿，一次性报出 8 条假缺件。
2. **对账算法本身是可信的。** 补上正确字段后，上游双票合计、下游单票、跨端利息 40,545、尾款 67,582.95 全部正确勾稽，缺件判定也随文档齐套而自动消失。
3. **最先该修的不是对账，是字段抽取 + 盖章检测。** OCR 已验证可用（置信度 0.99、关键信息全中），说明差距在"规则覆盖"，属于可控工作量；盖章检测则是算法本身失效，需要重做。
4. **两条 CRITICAL/口径问题必须一起修**：回单款项性质（保证金被当货款 → 误报 +636,795）和付款回单缺件严重度，否则真实缺陷会被误报噪声掩盖。
