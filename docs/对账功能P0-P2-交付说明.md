# 对账功能 P0–P2 交付说明

> 本文说明本轮「发现问题 → 交付问题 → 跟踪问题」补齐的 7 项功能（P0 2 项、P1 3 项、P2 2 项），
> 以及实施时确定的边界与限制。业务口径见 `对账核对范围-上游三项下游两项.md`，
> 规则通用性见 `对账规则通用性-自检与本次补丁.md`。

## 一、交付总览

| 优先级 | 功能 | 后端 | 前端入口 |
|---|---|---|---|
| P0-1 | 对账结果导出 Excel | `GET /api/reconciliation/export` | 对账明细页「导出 Excel」 |
| P0-2 | 差异处理闭环 | `POST /reports/{business_no}/resolve` | 抽屉差异表「处理」弹窗 |
| P1-1 | 外部明细导入 | `/external-details*`（4 个端点） | 「外部明细」页 |
| P1-2 | 缺件催办 | `POST /reports/{business_no}/urge`、`GET /urge-list` | 抽屉「催办」+「催办清单」页 |
| P1-3 | 客户视角 / 期间视角 | `GET /summary?group=customer\|month` | 「客户视角」「期间视角」页 |
| P2-1 | 定时巡检 + 变化提醒 | `/schedule`（GET/PUT）、`/schedule/clear-changes` | 工具栏「每日自动对账」开关 |
| P2-2 | 发票号跨业务线唯一校验 | `GET /invoice-uniqueness` | 「外部明细」页底部区块 |

## 二、P0-1 导出 Excel

`backend/services/reconciliation_export.py` 的 `build_workbook(rows)` 输出四个 sheet：

1. **对账明细**（18 列）——业务线、上下游合同、合同额、上下游结算、应收/实收利息、付款/收款、期间、状态、差异数等；
2. **差异明细**（13 列）——业务线、方向、角色、类型、严重级别、标题、期望、实际、处理方式、备注、是否新增、单据 ID；
3. **待补资料**（8 列）——缺件清单，含方向、角色、严重级别、处理方式；
4. **未归属单据**（2 列）——库里没挂上业务线的单据。

格式：表头深蓝底白字、冻结首行、自动换行、金额列 `#,##0.00`；`_num()` 兼容千分位与 `¥`。
文件名 `reconciliation_YYYYMMDD_HHMM.xlsx`，通过 `StreamingResponse` + `Content-Disposition` 返回。
支持 `status`、`keyword` 筛选，导出内容与当前列表筛选一致。

## 三、P0-2 差异处理闭环

- `DiffItem` 扩展 `key` / `is_new` / `resolution`；`diff_key()` 对
  `type|direction|role|expected|actual|document_ids` 取 sha1 前 12 位，保证同一差异跨轮稳定。
- 每次 `run()` 先读上一轮快照 `prev_snapshots`，再对每条差异 `_merge_resolution`：
  首次出现 `is_new=None`；上轮没有 → `True`（新增）；上轮有 → `False`（遗留），并继承处理记录。
- 处理方式六种：`supplement`（待补单）、`adjust`（待调账）、`pending`（待确认）、
  `false_positive`（误报）、`ignore`（忽略）、`reopen`（撤销处理）。
  前两者计入 `diff_count` 仍待办，`false_positive` / `ignore` 关闭差异（`ignored=True`），
  `reopen` 清空处理记录并恢复待办。
- 详情接口新增 `resolved_diffs`：上一轮存在、本轮消失的差异（含消失时间），用于「已解决」列表。
  `has_docs=False`（未上传资料）时不判定已解决，避免把「没核」误报成「已解决」。

## 四、P1-1 外部明细导入

`external_details` 表（`SCHEMA_VERSION=7`，迁移 `_migrate_create_external_details`，两个索引）。
导入端点 `POST /api/reconciliation/external-details/import`（multipart：`file` + 可选 `mapping` JSON）。

- 只读第一个 sheet、表头取第一行；列名支持别名（业务线号/业务编号、日期/发生日期、金额、类型/方向、备注），
  必要时用 `mapping` 手工指定；缺必要列直接 400。
- 金额容错千分位、`¥`、括号负数；日期兼容多种字符串格式与 Excel 序列号；
  方向按关键词判定，没有关键词时按金额正负，仍判断不出默认 `receipt`。
- 整批共用一个 `EXT+时间戳+4位hex` 批次号，支持按批次整体删除。

**关键边界：外部明细只作为参考口径展示与聚合，不参与任何判定，不生成差异、不改变状态。**
原因是下游一客户多业务线、回款无法按业务线拆分，若强行参与判定会大面积误报。

## 五、P1-2 催办

- `POST /reports/{business_no}/urge` 把催办记录写进报告 payload 的 `urges`（次数、时间、备注），
  不建独立表；`run()` 重算时保留该字段，不会被覆盖。
- `GET /urge-list` 扫描全部报告，收集未关闭的 `MISSING_DOC` 差异所涉角色，
  输出 `missing_roles`、`urge_count`、`last_urged_at`、`last_note`，按催办次数倒序。

## 六、P1-3 客户 / 期间聚合

`GET /summary?group=customer|month`：客户取 payload `customer`（空则归入「未填写采购商」），
期间取新增 payload `period`（下游合同日期优先，正则取 `YYYY-MM`）。
聚合采购结算、销售结算、实收利息、付款/收款、外部收款、差异数与四种状态计数，
按「错误×10 + 警告」倒序，便于先看最需要处理的客户/月份。

## 七、P2-1 定时巡检

`backend/services/reconciliation_scheduler.py`：

- 状态存 `data/reconciliation_schedule.json`（路径由 `settings.LOG_DIR` 的父目录派生）。
- cron 只接受「分 时 * * *」且分/时为纯数字；`*/n`、区间、列表、周字段一律返回
  「目前只支持每天固定时刻」，接口 400，不做静默降级。
- `run_once()` 执行前后各取一次 `_snapshot()`（业务线 → (状态, 差异数)）对比，
  新增业务线、差异数变大、状态变化都算 `changed`，写入 `changed_businesses` 供页面提醒。
- 执行失败写 `last_error` 而不是吞掉异常；守护线程每 30 秒轮询，同一分钟只触发一次。
- `backend/main.py` 的 lifespan 启动时 `sync_recon()`、退出时 `stop_recon()`。
- 变化提醒目前只落在页面上（顶部黄色提示条 + 「标记为已读」），**未接**系统通知 / 邮件 / 飞书消息。

## 八、P2-2 发票号跨业务线校验

`GET /invoice-uniqueness`：从各报告矩阵的 `document_ids` 建「单据 → 业务线」映射，
再查 `DocumentField.field_name == "invoice_no"`，长度 ≥ 6 的号码按业务线集合，
命中 > 1 条线即输出 `{invoice_no, business_nos, title}`。
用于发现同一张发票被两个业务线同时挂账（重复入账或拆单错误）。

## 十、已知限制

1. 外部明细不参与判定（见四）。等下游回款能按业务线拆分后，再决定是否升级为判定输入。
2. 催办记录存在 `report_json` 里，不做独立表；跨报告统计依赖 `urge-list` 全量扫描。
3. 定时巡检的通知只在页面展示，没有外部推送渠道。
4. cron 只支持每天一个固定时刻；需要「每周一 / 每小时」再扩解析器。
5. 发票号唯一性只覆盖已归属单据；未归属发票不参与比对。
